# Контракт Workspace

## Назначение

Этот файл кратко фиксирует репозиторный контракт для production
Obsidian-workspace, с которым работает ассистент.

## Source of Truth

- Production workspace — это отдельный Git-репозиторий, корневой путь к
  которому задается явно.
- `.workspace/` в этом репозитории используется только как reference example и
  не является production write target.
- Долговременное состояние хранится в production workspace, репозиторных
  конфигурационных файлах и репозиторных логах.
- `runtime/` может содержать временные execution artifacts, но никогда не
  является источником истины.

## Обязательная структура `v1`

### Обязательные сферы

- `Работа`
- `Дом`
- `Авто`
- `Здоровье`
- `Семья`

Каждая обязательная сфера должна содержать:

- `Цели.md`
- `Тактические цели.md`
- `Операционные задачи.md`
- `Артефакты/`

### Обязательные общие артефакты

- `Цели на 5 лет.md`
- общую семантику шаблона сферы на основе `.workspace/!Общее/Шаблон сферы`
- репозиторное место для конфигурации ассистента
- репозиторное место для журналов ассистента
- сохраненное клиентское состояние `.obsidian/`, если оно существует

## Planning Chain

Контракт сохраняет явные anchor points для цепочки:

`Операционная задача -> Цель месяца -> Годовая цель -> Цель на 5 лет`

Следующие этапы могут уточнить точный синтаксис ссылок, но сами anchor points и
роли заметок уже являются частью контракта.

## Ручная работа через Obsidian

- Обязательные артефакты должны оставаться читаемыми и редактируемыми прямо в
  Obsidian.
- Ассистент не может делать Telegram единственным способом просмотра или
  изменения долговременных planning artifacts.
- Нормализация может добавлять недостающую структуру, но не может без
  подтверждения переписывать уже существующий пользовательский смысл.
- Layout и настройки `.obsidian/` считаются пользовательским working state.

## Режимы нормализации

- `report-only`: обнаруживать отклонения и формировать audit report без
  применения изменений к файловой структуре
- `apply-safe-structure`: создавать недостающую обязательную структуру и
  добавлять безопасные структурные секции без перезаписи существующего
  пользовательского содержимого

## Границы автономности

- `auto-allowed`: создавать недостающие обязательные каталоги и note stubs,
  добавлять недостающие безопасные структурные секции, создавать задокументированные
  config/log anchors
- `proposal-only`: предлагать переименования, консолидацию заметок или
  дополнительные semantic links
- `requires-confirmation`: удалять, архивировать, перемещать, переименовывать,
  сливать или перезаписывать существующее пользовательское содержимое;
  переписывать `.obsidian/`; переносить пользовательские файлы между сферами

## Пользовательские сферы

- Дополнительные top-level сферы разрешены.
- Нормализация должна сохранять их даже если они находятся вне минимального
  набора `v1`.
- Ассистент может рекомендовать привести их к контракту, но не может
  автоматически удалять или переименовывать такие сферы.
