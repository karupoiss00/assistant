# Feature Specification: Workspace Foundation

**Feature Branch**: `002-workspace-foundation`

**Created**: 2026-06-08

**Status**: Draft

**Input**: User description: "Stage 1: Workspace Foundation. Определи контракт Obsidian-workspace, с которым будет работать ассистент. Для проектирования используй текущее состояние в папке `.workspace` как reference example, включая реальные сферы, шаблон `.workspace/!Общее/Шаблон сферы`, существующие заметки и `.obsidian`-структуру. При этом сама фича не должна предполагать, что в проде workspace всегда лежит в `.workspace`: ассистент в будущем должен уметь работать с произвольным git-репозиторием Obsidian, путь к которому задается конфигурацией. Спецификация должна описать обязательную структуру workspace, правила нормализации существующего пространства без потери пользовательских данных, что считается source of truth, какие части workspace изменяемы автоматически, а какие только по подтверждению пользователя."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Understand Workspace Contract (Priority: P1)

Как пользователь, я хочу иметь явный контракт Obsidian-workspace, чтобы
ассистент и я одинаково понимали, какие каталоги, заметки и связи считаются
обязательными, а какие являются пользовательским содержимым.

**Why this priority**: Пока контракт workspace не зафиксирован, последующие
этапы не смогут надёжно записывать данные, проверять целостность структуры и
объяснять, почему тот или иной файл считается источником истины.

**Independent Test**: Пользователь открывает описание workspace и может без
дополнительных пояснений определить обязательные сферы, общие артефакты,
шаблонные элементы и роль `.obsidian` в рабочем пространстве.

**Acceptance Scenarios**:

1. **Given** reference workspace в папке `.workspace`, **When** контракт
   формализован, **Then** он явно описывает обязательные сферы, общие артефакты,
   шаблон `.workspace/!Общее/Шаблон сферы`, существующие типы заметок и место
   служебных настроек Obsidian.
2. **Given** реальный production workspace может находиться в другом git-репозитории,
   **When** пользователь читает спецификацию, **Then** он видит, что путь к
   workspace является конфигурируемым, а `.workspace` используется только как
   reference example для проектирования.

---

### User Story 2 - Normalize Existing Workspace Safely (Priority: P2)

Как пользователь, я хочу, чтобы ассистент мог приводить существующее
Obsidian-пространство к обязательному контракту без потери уже созданных
заметок, артефактов и пользовательского контекста.

**Why this priority**: Реальное пространство уже содержит данные, поэтому
создание нового идеального скелета с нуля не решает задачу `v1`; нужна
безопасная нормализация текущего состояния.

**Independent Test**: Пользователь сравнивает workspace до и после
нормализации и убеждается, что отсутствующие обязательные элементы добавлены,
существующие пользовательские записи сохранены, а спорные изменения не были
применены скрытно.

**Acceptance Scenarios**:

1. **Given** workspace содержит обязательные сферы, но некоторые элементы
   заполнены неравномерно, **When** ассистент выполняет нормализацию, **Then**
   он добавляет недостающие обязательные части без удаления существующих
   заметок и артефактов.
2. **Given** внутри workspace уже есть пользовательские заметки, включая
   рабочие артефакты и `.obsidian`-настройки, **When** ассистент приводит
   структуру к контракту, **Then** он сохраняет пользовательское содержимое и
   не переписывает его без отдельного подтверждения.

---

### User Story 3 - Define Source of Truth and Write Boundaries (Priority: P3)

Как пользователь, я хочу заранее понимать, какие части workspace являются
источником истины, какие изменения ассистент может делать автоматически, а
какие только предлагать, чтобы не потерять доверие к системе.

**Why this priority**: Даже на фундаментальном этапе продукт должен чётко
показывать границы автоматизации; иначе любые дальнейшие сценарии с capture,
review и linking будут восприниматься как риск.

**Independent Test**: Пользователь может перечислить, какие артефакты ассистент
вправе создать или дополнить сам, какие действия требуют подтверждения и где
искать историю таких изменений.

**Acceptance Scenarios**:

1. **Given** workspace contract описан, **When** пользователь изучает правила
   работы ассистента, **Then** он видит, какие структурные изменения относятся к
   auto-allowed, какие являются proposal-only, а какие требуют confirmation.
2. **Given** ассистент меняет структуру workspace, **When** пользователь
   проверяет результат, **Then** он может отличить обязательные структурные
   обновления от изменений пользовательского смысла и найти историю операций.

### Edge Cases

- Что происходит, если production workspace не содержит одну из пяти стартовых
  сфер или использует дополнительную пользовательскую сферу?
- Как нормализация ведёт себя, если в сфере уже есть `Цели.md`,
  `Тактические цели.md` и `Операционные задачи.md`, но они частично расходятся с
  шаблоном `.workspace/!Общее/Шаблон сферы`?
- Что считается обязательным минимумом для `.obsidian`, если конкретный
  workspace хранит дополнительные пользовательские настройки и layout-файлы?
- Как ассистент должен обходиться с артефактами и заметками, которые не входят в
  обязательный контракт, но уже существуют внутри workspace?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST описывать workspace как отдельный Obsidian-совместимый
  git-репозиторий с конфигурируемым корневым путём, а не как жестко заданную
  папку `.workspace`.
- **FR-002**: Система MUST использовать текущее содержимое `.workspace` только
  как reference example для формализации workspace contract.
- **FR-003**: Система MUST фиксировать обязательные стартовые сферы `Работа`,
  `Дом`, `Авто`, `Здоровье` и `Семья` как часть `v1` workspace contract.
- **FR-004**: Система MUST фиксировать обязательный набор сферовых артефактов:
  `Цели.md`, `Тактические цели.md`, `Операционные задачи.md` и каталог
  `Артефакты/`.
- **FR-005**: Система MUST фиксировать общие артефакты workspace, включая
  `Цели на 5 лет`, общие шаблоны, место для конфигурации поведения ассистента и
  место для журналов действий.
- **FR-006**: Система MUST определять `.workspace/!Общее/Шаблон сферы` как
  reference pattern для обязательной структуры сфер, не считая этот путь
  обязательным продовым расположением.
- **FR-007**: Система MUST определять роль `.obsidian` как части рабочего
  пространства, которая хранит клиентские настройки Obsidian и должна
  сохраняться при нормализации, если нет явного подтверждения на её замену.
- **FR-008**: Система MUST описывать правила нормализации существующего
  workspace: добавление отсутствующих обязательных элементов допускается без
  потери пользовательских заметок и артефактов.
- **FR-009**: Система MUST различать структурные изменения и смысловые изменения
  пользовательского содержимого.
- **FR-010**: Система MUST относить создание отсутствующих обязательных
  структурных элементов к auto-allowed действиям.
- **FR-011**: Система MUST относить переименование, удаление, архивирование,
  перезапись существующих пользовательских заметок и изменение `.obsidian`
  настроек к действиям, требующим подтверждения пользователя, если это меняет
  существующий смысл или рабочую среду.
- **FR-012**: Система MUST фиксировать, что обязательные связи
  `Операционная задача -> Цель месяца -> Годовая цель -> Цель на 5 лет`
  являются частью контракта workspace, даже если их конкретная реализация
  будет уточняться на следующих этапах.
- **FR-013**: Система MUST считать источником истины содержимое production
  workspace, его конфигурацию и журналы, а не временные runtime-файлы вне
  workspace.
- **FR-014**: Система MUST обеспечивать ручную читаемость и редактируемость
  обязательных артефактов напрямую через Obsidian без обязательного использования
  Telegram.
- **FR-015**: Система MUST фиксировать требование к хранению истории действий
  ассистента минимум за 30 дней внутри репозиторных журналов.

### Key Entities *(include if feature involves data)*

- **Workspace Root**: Корень Obsidian git-репозитория, с которым работает
  ассистент; путь к нему задаётся конфигурацией.
- **Reference Workspace**: Текущее содержимое `.workspace`, используемое для
  проектирования и валидации workspace contract.
- **Сфера**: Жизненная область `v1`, для которой существуют цели, тактические
  цели, операционные задачи и артефакты.
- **Шаблон сферы**: Reference pattern обязательной структуры и ожидаемого
  содержания сферовых файлов.
- **Общий артефакт**: Верхнеуровневая заметка или каталог, который относится ко
  всему workspace, а не к одной сфере.
- **Структурная нормализация**: Приведение существующего workspace к
  обязательному контракту без потери пользовательских данных.
- **Смысловое изменение**: Любое действие, меняющее содержание существующей
  заметки, пользовательскую интерпретацию или рабочую среду сверх обязательной
  структурной инициализации.

## Repository Impact *(mandatory for stateful features)*

- **Authoritative Files**: Production workspace root и его заметки, каталоги
  сфер, общие артефакты, пользовательские артефакты, `.obsidian`-настройки,
  репозиторные конфиги поведения ассистента и журналы действий.
- **Derived/Ephemeral State**: Локальная папка `.workspace` в этом проекте
  служит reference example; runtime-файлы и служебные кэши вне production
  workspace не считаются источником истины.
- **Link Integrity**: Контракт workspace MUST сохранять явные места и правила
  для цепочки `задача -> месяц -> год -> 5 лет`; нормализация не должна скрыто
  разрушать существующие ссылки, вложения и пользовательские артефакты.

## Autonomy & Confirmation Boundaries *(mandatory)*

- **Auto-Allowed Actions**: Создание отсутствующих обязательных каталогов,
  создание отсутствующих обязательных заметок, добавление недостающих
  структурных секций, создание выделенного места для журналов и конфигурации.
- **Proposal-Only Actions**: Рекомендации по приведению нестандартных названий к
  контракту, предложения по унификации пользовательских заметок и предложения по
  дополнительным смысловым связям между сущностями.
- **Requires-Confirmation Actions**: Удаление, архивирование, слияние,
  переименование существующих заметок, перенос пользовательских файлов между
  разделами, перезапись `.obsidian`-настроек и любое изменение, которое
  модифицирует уже существующий пользовательский смысл.
- **User Notification**: После каждой нормализации пользователь получает
  перечень созданных или дополненных обязательных элементов, список затронутых
  путей и отдельный список действий, которые были только предложены и не
  выполнены автоматически.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может по одной спецификации определить обязательную
  структуру workspace, его source of truth и границы автоматических изменений не
  более чем за 15 минут.
- **SC-002**: Контракт workspace покрывает все пять стартовых сфер, шаблон
  сферы, общие артефакты и роль `.obsidian` без оставшихся критических пробелов.
- **SC-003**: В 100% проверенных сценариев нормализации отсутствующие
  обязательные структурные элементы могут быть добавлены без удаления
  существующих пользовательских заметок.
- **SC-004**: Пользователь может отличить auto-allowed, proposal-only и
  requires-confirmation действия по спецификации без обращения к исходному коду
  или дополнительным инструкциям.
- **SC-005**: Production workspace path может быть задан независимо от `.workspace`,
  и это ограничение явно отражено в спецификации как часть контракта.

## Assumptions

- `.workspace` отражает достаточно репрезентативное текущее состояние рабочего
  Obsidian-пространства, чтобы служить reference example для `Stage 1`.
- Стартовый набор сфер `v1` совпадает с текущими сферами в reference workspace.
- Пользовательские заметки и `.obsidian`-настройки рассматриваются как ценные
  данные по умолчанию и не должны считаться расходным материалом при
  нормализации.
- Формат конкретных конфигурационных файлов и логов может быть уточнён на
  следующих этапах, если сохраняются зафиксированные здесь границы source of
  truth и автономии.

## Observability & Audit *(mandatory for state-changing features)*

- **Events Logged**: Обнаружение нарушений workspace contract, создание
  отсутствующих обязательных элементов, предложения по спорным изменениям,
  подтверждённые пользователем смысловые изменения и ошибки нормализации.
- **Traceability**: Каждое структурное действие должно быть сопоставимо с
  конкретным путём внутри workspace и записью в журнале, чтобы пользователь мог
  понять, что было добавлено автоматически, а что изменено по подтверждению.
- **Retention / Review Path**: Журналы действий ассистента хранятся внутри
  production workspace минимум 30 дней и остаются доступными для ручной
  проверки через Obsidian и git history.
