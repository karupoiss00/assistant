# IMPLEMENTATION_PLAN.md

## 1. Цель проекта

Нужно реализовать персонального ассистента на базе OpenClaw, который будет работать на VPS, общаться со мной через Telegram и вести мой Obsidian vault как git-репозиторий.

Ассистент должен помогать с регулярным планированием, рефлексией, сбором входящих заметок и задач, а также поддерживать личную базу знаний в Obsidian.

Основные сценарии:

1. Утром присылать план дня.
2. В течение дня принимать заметки, мысли и todo через Telegram.
3. Вечером проводить закрытие дня:
   - рефлексия;
   - разбор влетевших за день задач;
   - планирование задач на завтра или будущие даты.
4. Записывать всё в Markdown-файлы Obsidian vault.
5. Синхронизировать изменения через git.
6. Не терять данные при ошибках git, конфликтах или падении сервиса.

## 2. Целевая архитектура

```text
VPS
├── OpenClaw daemon
├── Telegram bot / Telegram channel
├── Obsidian vault as git repository
├── cron jobs / scheduled tasks
├── agent prompts / skills
├── safe git wrapper
```

Основной поток:

```text
User
  ↓

  ↓
OpenClaw on VPS
  ↓

  ↓

```

```text

```

Резервная очередь для сообщений, которые не удалось записать из-за ошибки git:

```text

```

Логи:

```text
~/assistant/logs
```

Конфиг:

```text
~/assistant/config.json
```

Секреты:

```text
~/assistant/.env
```

## 3. Базовые требования

Ассистент должен:

1. Работать на VPS как daemon.
2. Быть доступен через Telegram с разных устройств.
3. Принимать сообщения только от моего Telegram user id.
4. Работать с Obsidian vault как с git-репозиторием.
5. Перед записью всегда делать `git pull --rebase`.
6. После записи делать `git add`, `git commit`, `git push`.
7. При git-конфликте не перетирать файлы автоматически.
8. При ошибках сохранять входящее сообщение в `~/assistant/pending`.
9. Не удалять файлы без явного подтверждения.
10. Не делать массовые изменения без подтверждения.
11. Не открывать OpenClaw Gateway наружу в интернет.
12. Все опасные операции делать только после подтверждения пользователя.

## 4. Важная проверка перед реализацией

Перед началом реализации агент должен проверить актуальную документацию OpenClaw:

1. Как правильно установить OpenClaw на Linux/VPS.
2. Как включить daemon mode.
3. Как подключить Telegram.
4. Как настроить cron/scheduled jobs.
5. Как добавлять custom skills/tools.
6. Где хранится конфигурация.
7. Как правильно ограничить доступ к Telegram-боту.

После проверки агент должен адаптировать команды установки под актуальную версию OpenClaw.

## 10. Git workflow

Все изменения в vault должны проходить через безопасную функцию.

Псевдологика:

```text
function updateVault(change):
  cd ~/assistant/vault

  git status
  git pull --rebase

  if pull failed:
    save change to ~/assistant/pending/YYYY-MM-DD-HH-mm-ss.md
    notify user in Telegram
    stop

  apply change

  git diff

  if no changes:
    notify user that nothing changed
    stop

  git add .
  git commit -m "assistant: <short description>"
  git push

  if push failed:
    notify user in Telegram
    save diagnostic info to logs
    stop

  notify user if needed
```

Требования:

1. Не делать commit без изменений.
2. Commit message должен быть понятным.
3. Каждое пользовательское сообщение должно либо попасть в vault, либо в pending.
4. При конфликте git нельзя делать auto-resolve через overwrite.
5. При конфликте нужно написать пользователю:

```text
Не смог записать изменение в Obsidian из-за git-конфликта. Я сохранил сообщение в pending, чтобы оно не потерялось.
```

Формат pending-файла:

```markdown
# Pending message

created:: YYYY-MM-DD HH:mm
source:: telegram
reason:: git_pull_failed | git_push_failed | conflict

## Original message

...
```

## 11. Telegram allowlist

Ассистент должен обрабатывать сообщения только от разрешённых Telegram user id.

Если пишет неизвестный пользователь:

1. Не выполнять команды.
2. Не раскрывать данные.
3. Ответить нейтрально или ничего не отвечать.
4. Записать событие в лог.

Псевдологика:

```text
if telegramUserId not in config.telegramAllowedUserIds:
  log unauthorized access
  return
```

## 12. Команды Telegram

### 12.1 Capture: заметка

Паттерны:

```text
note: текст
заметка: текст
мысль: текст
наблюдение: текст
```

Действие:

1. Сделать `git pull --rebase`.
2. Добавить запись в `00-inbox/inbox.md`.
3. Сделать commit + push.
4. Ответить коротко:

```text
Записал в inbox.
```

Формат записи:

```markdown
- YYYY-MM-DD HH:mm — текст #note
```

---

### 12.2 Capture: todo

Паттерны:

```text
todo: текст
туду: текст
задача: текст
сделать: текст
```

Действие:

1. Добавить задачу в `00-inbox/inbox.md`.
2. Сохранить timestamp.
3. Сделать commit + push.

Формат:

```markdown
- [ ] текст #todo created:: YYYY-MM-DD HH:mm
```

Ответ:

```text
Добавил задачу в inbox.
```

---

### 12.3 Todo с областью

Паттерны:

```text
todo work: текст
todo home: текст
todo car: текст
todo relationships: текст
```

Аналоги на русском:

```text
задача работа: текст
задача дом: текст
задача машина: текст
задача отношения: текст
```

Действие:

1. Если область распознана — добавить в соответствующий файл:
   - `20-areas/work.md`
   - `20-areas/home.md`
   - `20-areas/car.md`
   - `20-areas/relationships.md`
2. Если область не распознана — добавить в inbox.
3. Сделать commit + push.

Формат:

```markdown
- [ ] текст created:: YYYY-MM-DD HH:mm
```

---

### 12.4 План дня

Паттерны:

```text
план
план на день
что у меня сегодня
покажи план
```

Действие:

1. Сделать `git pull --rebase`.
2. Создать today daily note, если её нет.
3. Прочитать:
   - today's daily note;
   - inbox;
   - незавершённые задачи за последние 7 дней;
   - tomorrow daily note, если пользователь просит план на завтра.
4. Сформировать короткий план.
5. Отправить в Telegram.

Формат ответа:

```text
План на сегодня:

Главный фокус:
1. ...

Ещё важно:
- ...
- ...

Из хвостов:
- ...

Рекомендация:
...
```

Правила:

1. Не предлагать больше 1–3 главных фокусов.
2. Не перегружать день задачами.
3. Отделять «главный фокус» от «можно сделать».
4. Если задач слишком много — явно сказать, что день перегружен.

---

### 12.5 Рефлексия

Паттерны:

```text
рефлексия
вечерняя рефлексия
```

Это не отдельный финальный сценарий, а первая часть сценария «закрытие дня».

Действие:

1. Задать вопросы.
2. Дождаться ответа.
3. Структурировать ответ.
4. Записать в today's daily note в раздел `## Рефлексия`.
5. После этого перейти к разбору влетевших задач.

Вопросы:

```text
1. Что сегодня получилось?
2. Что не получилось или застряло?
3. Что забрало больше всего энергии?
4. Что нужно перенести?
5. Какой один вывод дня?
```

---

### 12.6 Закрытие дня

Паттерны:

```text
закрыть день
завершить день
вечер
shutdown
```

Это главный вечерний сценарий.

Сценарий состоит из трёх этапов:

```text
1. Рефлексия
2. Разбор влетевших задач
3. Планирование завтра
```

## 13. Evening shutdown flow

### 13.1 Этап 1: рефлексия

Ассистент задаёт вопросы:

```text
Давай закроем день.

1. Что сегодня получилось?
2. Что не получилось или застряло?
3. Что забрало больше всего энергии?
4. Что нужно перенести?
5. Какой вывод дня?
```

После ответа:

1. Структурировать ответ.
2. Записать его в today's daily note.
3. Кратко отразить 1–3 наблюдения.

Пример ответа:

```text
Записал рефлексию.

Вижу, что день был скорее реактивный: много входящих и мало глубокой работы. На завтра лучше выбрать один главный фокус и заранее оставить слот под разбор хвостов.
```

---

### 13.2 Этап 2: разбор влетевших задач

После рефлексии ассистент должен собрать входящие за день:

1. Задачи из `00-inbox/inbox.md`, созданные сегодня.
2. Заметки из `00-inbox/inbox.md`, созданные сегодня.
3. Задачи из today's daily note в разделе `## Входящие за день`.
4. Незавершённые задачи из today's daily note.
5. Новые задачи, которые пользователь упомянул в рефлексии.

Ассистент показывает список:

```text
Я вижу такие входящие за сегодня:

1. [ ] Заказать план электрики строителю
2. [ ] Обсудить передачу микросервисов
3. note: идея про агента для Obsidian
4. [ ] Проверить саппортовые метрики

Давай разложим их.
```

Для каждого пункта нужно предложить действие:

```text
A. Запланировать на завтра
B. Запланировать на конкретную дату
C. Перенести в проект
D. Перенести в область
E. Оставить в inbox
F. Отметить как неактуальное
```

Ассистент не должен удалять задачи молча.

Если пользователь отвечает свободным текстом, ассистент должен распарсить намерение.

Пример:

```text
электрику на завтра, микросервисы на следующую неделю, идею в knowledge, метрики оставить в inbox
```

Ассистент должен показать план изменений и попросить подтверждение:

```text
Понял так:

- Заказать план электрики строителю → завтра
- Обсудить передачу микросервисов → следующая неделя
- Идея про агента для Obsidian → knowledge
- Проверить саппортовые метрики → оставить в inbox

Применить?
```

Только после подтверждения применять изменения.

---

### 13.3 Этап 3: планирование завтра

После разбора входящих ассистент должен предложить предварительный план на завтра.

Он учитывает:

1. Задачи, явно перенесённые на завтра.
2. Незавершённые задачи сегодняшнего дня.
3. Важные задачи из inbox.
4. Уже существующую tomorrow daily note.
5. Ограничение по фокусу: не больше 1–3 главных задач.

Формат:

```text
Предварительный план на завтра:

Главный фокус:
1. ...

Ещё важно:
- ...
- ...

Можно сделать, если останется время:
- ...

Оставляю в backlog:
- ...
```

После этого ассистент спрашивает:

```text
Записать это в план на завтра?
```

После подтверждения:

1. Создать или обновить tomorrow daily note.
2. Добавить задачи в разделы:
   - `## План дня`;
   - `## Задачи`.
3. В today's daily note отметить, что задачи перенесены.
4. Обработанные элементы в inbox перенести из `Unprocessed` в `Processed` или пометить как processed.
5. Сделать commit + push.

## 14. Утренний план

Утренний cron запускается каждый день в configured time, например 09:00.

Задача:

```text
Сформируй план дня для пользователя. Прочитай today's daily note, inbox, незавершённые задачи за последние 7 дней и предварительный план, созданный вечером. Отправь короткий план в Telegram.
```

Утренний план должен:

1. Показывать главный фокус.
2. Показывать задачи дня.
3. Подсвечивать перегруз.
4. Предлагать, что можно выкинуть/перенести.
5. Напоминать о влетевших, если они не разобраны.

Пример:

```text
Доброе утро.

Главный фокус:
1. Довести план по ассистенту до MVP

Важно:
- Проверить задачу по микросервисам
- Разобрать 2 пункта из inbox

Если останется время:
- Навести порядок в заметках по work

День выглядит умеренно загруженным. Лучше не добавлять больше одной крупной задачи.
```

## 15. Вечерний cron

Вечерний cron запускается каждый день в configured time, например 22:30.

Задача:

```text
Напомни пользователю закрыть день. Проведи рефлексию, затем разбери влетевшие за день задачи и помоги спланировать завтра.
```

Сообщение:

```text
Пора закрыть день.

Сначала короткая рефлексия, потом разберём влетевшие задачи и соберём план на завтра.
```

Если пользователь не отвечает, ничего не делать, кроме мягкого напоминания максимум один раз.

---

## 16. Недельное ревью

Недельный cron запускается раз в неделю, например в воскресенье вечером.

Задача:

```text
Собери ревью недели по daily notes за последние 7 дней. Найди достижения, повторяющиеся проблемы, незавершённые задачи и предложи фокус следующей недели.
```

Формат:

```text
Итоги недели:

Что получилось:
- ...

Повторяющиеся проблемы:
- ...

Хвосты:
- ...

Предложение на следующую неделю:
- главный фокус: ...
- не брать в работу: ...
```

Запись в weekly note делать только после подтверждения.

## 17. Agents / Skills

Для MVP не нужно делать сложную multi-agent систему. Но логически разделить поведение нужно так.

### 17.1 Capture Agent

Ответственность:

1. Принимать заметки, мысли, todo.
2. Быстро и безопасно складывать их в inbox.
3. Не пытаться слишком умно классифицировать.
4. Не терять данные.

Вход:

```text
note:
todo:
заметка:
мысль:
задача:
```

Выход:

```text
Markdown-запись в inbox или area file
```

---

### 17.2 Planning Agent

Ответственность:

1. Формировать план дня.
2. Читать daily notes.
3. Читать inbox.
4. Находить хвосты.
5. Предлагать реалистичный набор задач.

Правила:

1. Не больше 1–3 главных фокусов.
2. Не перегружать план.
3. Разделять:
   - главный фокус;
   - важно;
   - если останется время;
   - backlog.

---

### 17.3 Reflection Agent

Ответственность:

1. Проводить рефлексию.
2. Задавать вопросы.
3. Структурировать ответ.
4. Записывать результат в daily note.
5. Делать мягкие выводы.

Правила:

1. Не давить чувством вины.
2. Не писать мотивационную воду.
3. Помогать увидеть паттерны.
4. Давать 1–3 практичные рекомендации.

---

### 17.4 Shutdown Agent

Ответственность:

1. Закрывать день.
2. После рефлексии находить влетевшие задачи.
3. Помогать решить судьбу каждой задачи.
4. Формировать план на завтра.
5. Обновлять today и tomorrow daily notes.

Это ключевой вечерний агент.

## 18. Стиль поведения ассистента

Ассистент должен быть:

1. Спокойным.
2. Кратким.
3. Конкретным.
4. Без лишней мотивационной воды.
5. Без давления и обвинений.
6. Полезным как операционный помощник.
7. Мягко возвращающим к фокусу.

Плохой тон:

```text
Ты опять не справился.
Нужно срочно всё исправить.
Ты обязан закрыть все задачи.
```

## 19. Безопасность

Обязательные меры:

1. Не открывать OpenClaw Gateway наружу.
2. Использовать Telegram как основной интерфейс.
3. Разрешить доступ только моему Telegram user id.
4. Хранить secrets в `.env`.
5. Не коммитить `.env`.
6. Использовать отдельный SSH deploy key для vault repo.
7. Ограничить права ключа только одним git-репозиторием.
8. Не давать ассистенту доступ к лишним директориям VPS.
9. Не выполнять shell-команды из пользовательского сообщения напрямую.
10. Все destructive actions — только после подтверждения.

Права:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 600 ~/assistant/.env
```

## 21. Настройка git repo

Создать SSH-ключ на VPS:

```bash
ssh-keygen -t ed25519 -C "openclaw-vps-obsidian"
```

Показать публичный ключ:

```bash
cat ~/.ssh/id_ed25519.pub
```

Добавить ключ в GitHub/GitLab как deploy key с write access только для obsidian vault repo.

Склонировать vault:

```bash
cd ~/assistant
git clone git@github.com:USERNAME/obsidian-vault.git vault
```

Настроить git author:

```bash
cd ~/assistant/vault
git config user.name "Personal Assistant"
git config user.email "assistant@example.com"
```

Проверить push:

```bash
touch .assistant-test
git add .assistant-test
git commit -m "assistant: test commit"
git push
rm .assistant-test
git add .
git commit -m "assistant: remove test file"
git push
```

## 22. MVP scope

Сначала реализовать только MVP.

MVP включает:

1. OpenClaw работает на VPS как daemon.
2. Telegram-бот принимает сообщения только от моего user id.
3. Vault склонирован на VPS.
4. Команда `note:` пишет в inbox.
5. Команда `todo:` пишет в inbox.
6. Команда `план` формирует план дня.
7. Команда `рефлексия` запускает закрытие дня.
8. Закрытие дня включает:
   - рефлексию;
   - разбор влетевших задач;
   - планирование завтра.
9. После каждого изменения выполняется git commit + push.
10. При ошибке git сообщение сохраняется в pending.
11. Утренний cron присылает план.
12. Вечерний cron напоминает закрыть день.

Не включать в MVP:

1. Календарь.
2. YouTrack.
3. Автоматическое глубокое связывание заметок.
4. Сложную multi-agent архитектуру.
5. Полноценное недельное планирование.
6. Автоматическое удаление или массовый перенос файлов.

## 23. Acceptance criteria MVP

MVP считается готовым, если выполняются все пункты.

### 23.1 Telegram доступ

Я пишу боту в Telegram, и он отвечает.

Неавторизованный Telegram user id не может использовать бота.

---

### 23.2 Запись заметки

Я пишу:

```text
note: проверить идею с агентами для Obsidian
```

В `00-inbox/inbox.md` появляется запись:

```markdown
- YYYY-MM-DD HH:mm — проверить идею с агентами для Obsidian #note
```

После этого появляется git commit и push.

---

### 23.3 Запись задачи

Я пишу:

```text
todo: заказать план электрики строителю
```

В `00-inbox/inbox.md` появляется задача:

```markdown
- [ ] заказать план электрики строителю #todo created:: YYYY-MM-DD HH:mm
```

После этого появляется git commit и push.

---

### 23.4 План дня

Я пишу:

```text
план
```

Бот:

1. Создаёт today daily note, если её нет.
2. Читает inbox и хвосты.
3. Присылает короткий план дня.

---

### 23.5 Закрытие дня

Я пишу:

```text
закрыть день
```

Или:

```text
рефлексия
```

Бот:

1. Задаёт вопросы рефлексии.
2. Принимает мой ответ.
3. Записывает рефлексию в today daily note.
4. Показывает влетевшие за день задачи.
5. Помогает решить судьбу задач.
6. Формирует предварительный план на завтра.
7. После подтверждения записывает plan в tomorrow daily note.
8. Делает git commit + push.

---

### 23.6 Pending fallback

Если git pull или git push падает:

1. Бот не теряет пользовательское сообщение.
2. Бот сохраняет его в `~/assistant/pending`.
3. Бот пишет мне в Telegram, что запись не удалась.
4. Бот сообщает, где сохранён pending-файл.

---

### 23.7 Синхронизация с другими устройствами

После записи через Telegram изменения видны на другом устройстве после git pull/sync Obsidian vault.

## 29. Главное правило реализации

Сначала нужно получить работающий простой MVP:

```text

```

Потом:

```text
план → daily note
```

Потом:

```text

```

Не начинать со сложной архитектуры, календаря, YouTrack и умной базы знаний, пока не заработал базовый цикл.
